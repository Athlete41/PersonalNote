# 分层设计法

## 核心思想

设计应分层呈现，从最高层开始逐层往下细节越来越具体。核心原则与 [[设计]] 一致：在约束中找最优解，层数是手段不是目的。

**灵活性说明：** 这是为复杂项目、协作等场景准备的工具，不是硬性流程。从需求到代码可以走多种路径：

- **完整路径：** 需求 → L1 → L2 → L3 → L4（大型复杂项目）
- **简化路径：** 需求 → L1 → L2 → 代码（常规项目）
- **极简路径：** 需求 → L1 → 代码（简单功能）
- **直通路径：** 需求 → 代码（trivial 修改）

## 适配器

### 什么时候用？

| 场景 | 用不用？ | 为什么？ |
|:---|:---|:---|
| **需要多人协作**（对齐需求/方案评审） | ✅ **推荐用** | 每层每图有明确的受众和场合，能高效对齐各方认知 |
| **项目复杂**（涉及多个子系统/高并发/复杂规则） | ✅ **推荐用** | 分层把大问题切碎，逐层消化，减轻一次性认知负担，同时遍历各层能避免遗漏 |
| **单人做 trivial 修改**（改个文案/修个小bug） | ❌ **不用** | 需求 → 代码直通即可，分层是浪费 |

> **一句话判断：** 只要你觉得"这事儿有点复杂/牵扯人多"，那就值得至少走到 L1。

### 不是层越多越好——成本分析

L3 各图的设计依赖 L2 和 L1 的所有产出，L4 又依赖 L1~L3 的所有产出。**每下一层的信息量是上一层 + 本层新增的叠加，总工作量是一个递增数列之和：**

```
总成本 ≈ L1 + (L1+L2) + (L1+L2+L3) + (L1+L2+L3+L4)
       = 4×L1 + 3×L2 + 2×L3 + 1×L4
```

这意味着：
- **L1 最值钱**——投入产出比最高，它出现在每一项里
- **层越深边际成本越高**——L4 画一张图，你需要回顾 L1~L3 的所有上下文
- **每加一层，总成本不是+1，是+n**——所以默认走简化路径，只在你确信那层能带来足够价值时才画

### 装修房子类比

- **L1** = 跟家人确定"这间房做什么用、谁住、要多大"（不涉及水电怎么走）
- **L2** = 跟设计师说"这里要装插座、那里要走网线、用中央空调还是分体机"（定技术方向）
- **L3** = 跟施工队长说"这面墙里的电线怎么走、开关多高"（具体细节）
- **L4** = 电工实际接线操作（代码级，一般不画在图上）

**一句话记住：** 一层只说一件事，混层是混乱的根源。

**下次遇到这类情况会触发：**
- 要画设计图但不知道从哪开始时 → "用分层设计法拆解"
- 评审时图里信息太杂一看就乱 → "是不是混层了？把不同维度的拆开"
- 跟不同角色沟通 → "给老板看L1就够了，给开发看L2/L3"

## 通用维度：需求的五大原始维度

无论需求多复杂，都可以拆成这 5 个维度的混合，各层的每张图本质上是在这些维度上分配不同权重：

| 维度            | 问什么        | 示例                |
| :------------ | :--------- | :---------------- |
| **主体（Who）**   | 谁发起？       | 普通用户、VIP、管理员、外部系统 |
| **功能（What）**  | 做什么事？      | 下单、退款、查库存         |
| **规则（How约束）** | 怎么做才对？     | VIP 打 8 折、库存不足拦截  |
| **质量（How好）**  | 多快、多稳、多安全？ | 响应 <200ms、支持国产加密  |
| **环境（Where）** | 跑在哪儿？      | 内网、公有云、国产化芯片      |

## 通用维度：系统主要指标（六大质量属性）

> 系统"好不好"可以从六个主要指标来衡量，详见 [[概念/系统主要指标]]。

评估一个设计时，逐项问这六个问题——漏掉任何一个，对系统质量的评估就不完整。

| 维度       | 问什么                | 低分表现       |
| :------- | :----------------- | :--------- |
| **可靠性**  | 稳不稳？出故障能自动恢复吗？     | 凌晨被报警电话吵醒  |
| **安全性**  | 安不安全？会不会被攻破、越权？    | 用户看到了别人的数据 |
| **可维护性** | 改起来痛不痛？加个字段要改几个文件？ | 改一行代码重构三小时 |
| **性能**   | 快不快？响应时间和吞吐量达标吗？   | 用户说"这系统真慢" |
| **可扩展性** | 加功能/加流量扛得住吗？       | 双十一流量翻倍就挂了 |
| **可复用性** | 这个模块能拿到其他地方直接用吗？   | 新项目又要重写一遍  |

## 层长什么样？怎么写设计？

不同层可能关注点不一样，但是抽象程度一定是递减的，但是这还不够让我们知道层长什么样，这样就无法设计，那么这里就我们这样规定，由观察角色决定。
l1层应当是老板、PM、客户能看懂的并且有他们重点关注的内容(来自 **需求的五个维度** 和 **系统主要指标**)， 当然他们到底感兴趣那一部分，这需要揣摩，如果老板资金紧张需要快速开发是吧？那可能就在**系统主要指标**的一些属性里面，这里揣摩的过程非常复杂就不展开叙述。

|        | **观察角色**            |
| :----- | :------------------ |
| **L1** | 老板/PM/客户/架构师        |
| **L2** | 技术负责人/开发/运维/架构师<br> |
| **L3** | 开发<br>              |
| **L4** | 实现者<br>             |

### 可以使用的表示手段

确定了每层的观察角色之后，用四种图作为表示手段。每种图擅长反映不同的关注点：

| 图类型     | 擅长反映的关注点                                                       | 大致总结                 |
| :------ | :------------------------------------------------------------- | -------------------- |
| [[架构图]] | **主体(Who)**、**环境(Where)**——边界、模块划分、部署关系、存储结构(较低层级的) 等          | 反映静态多于动态             |
| [[时序图]] | **功能(What)**、**沟通**——交互顺序、消息传递、调用链路等动态关系                       | 动态、静态均有，动态侧重交互而非系统决策 |
| [[状态图]] | **规则(How约束)**、**质量(How好)**——状态变迁、条件守卫、SLA等动态关系                 | 反映动态多于静态，动态侧重规则      |
| [[流程图]] | **功能(What分支)**、**规则(How决策)**、**质量(How好)**——决策路径、异常处理、分支逻辑等动态关系 | 反映动态多于静态，动态决策。       |

## 表5：常见反模式表——每层最常犯的错

| 层      | 反模式                  | 问题             | 正确做法                             |
| :----- | :------------------- | :------------- | :------------------------------- |
| **L1** | 架构图里画技术细节（如微服务、消息队列） | L1混入L2信息，老板看不懂 | L1只画业务边界，技术细节放到L2                |
|        | 时序图里展开业务规则           | 图太膨胀，失去时序价值    | 规则只以消息名暗示，细化放到状态图/控制流图           |
|        | 流程图缺少状态校验            | 分支判断和状态没有联动    | 画流程图时旁边附加核心对象的状态变迁               |
| **L2** | 容器结构图里拆了内部组件         | L2混入L3，图太碎     | L2只画进程级，不画进程内部                   |
|        | 时序图没标同步/异步           | 开发实现时不确定阻塞行为   | 每条连线标注请求类型和同步/异步                 |
|        | 没画部署与质量图             | 只说了架构没说到运维     | 图3必须覆盖灾备、扩缩容、监控                  |
| **L3** | 一张图上画多个容器的内部组件       | 混层混容器，信息爆炸     | 一个容器一张L3图                        |
|        | 把每个Java类都画成组件        | 图太碎            | 组件是模块级别（Service/Repository）      |
|        | 连线上不写用途              | 看了不知道为什么调用     | "uses"、"persists"、"delegates to" |
| **L4** | 给CRUD画类图             | 浪费             | CRUD不需要L4，框架自己生成                 |
|        | 状态映射和代码不一致           | 文档作废           | 状态图需要精确到枚举值+守卫+动作                |

## 总览速查表

| 层      | 受众        | 核心价值          | 图1：结构    | 图2：交互    | 图3：状态     | 图4：决策          |
| :----- | :-------- | :------------ | :------- | :------- | :-------- | :------------- |
| **L1** | 老板/PM/客户  | 对齐需求，确定业务逻辑   | 架构图（边界）  | 时序图（时序）  | 状态图（规则）   | 控制流图（收口）       |
| **L2** | 架构师/技术负责人 | 确定物理架构，扛不扛得住  | 容器结构（进程） | 容器交互（链路） | 服务状态（模式）  | 运维决策（灾备）       |
| **L3** | 开发工程师     | 模块划分，接口定义     | 组件结构（模块） | 组件交互（调用） | 内部状态（状态机） | 异常处理（fallback） |
| **L4** | 实现者       | 精确领域建模，关键代码定义 | 核心类图（实体） | 方法时序（方法） | 状态映射（枚举）  | 算法逻辑（步骤）       |
