# Agent 协作准则

## 核心思想

**用 Agent 构建软件的第一步不是画图，也不是写 prompt——而是了解你的合作对象。**

Agent 不是万能工具，它有明显的长处和短板。知道它怎么沟通最有效、知道哪些事它能做好、哪些事它靠不住，才能在设计中有策略地分配任务。

---

## 第一步：了解合作对象（Agent）

### 沟通方法

没有通用的最优沟通方式——模型在变、配置在变。开始编码前，先试几次摸清当前 Agent 的偏好：

- **结构化 prompt vs 自然语言描述**
- **给例子（few-shot）vs 不给**
- **checklist 确认 vs 自由输出**
- **长篇上下文 vs 分段交互**

### 能力边界

把 Agent 的能力分为三个区域：

| 区域       | 含义                                    | 对应的策略                        |
| -------- | ------------------------------------- | ---------------------------- |
| **信任区**  | 它做得又快又好，你检查也发现不了问题                    | 放权，让它自由发挥                    |
| **不信任区** | 它经常出错，你必须亲自把控                         | 设计时显式约束、prompt 中重点强调、生成后必须检查 |
| **盲区**   | 它意识不到这里有坑、或根本做不到（比如无法获取某些信息），也不会主动告诉你 | 你来兜底或者想办法让 Agent 自己发现盲区      |

盲区最危险——Agent 意识不到自己在犯错，也不会主动告诉你。常见盲区：安全纵深防御、业务隐含假设、跨模块一致性约束、任何需要外部信息才能做出的判断。

**让 Agent 自己发现盲区：** 给外部信息接口（日志、schema、文档）、多轮反问列出不确定点、反例引导、交叉验证。目的是把盲区暴露成可见的问题。

盲区不固定。换模型、换配置、换任务都不一样。了解 Agent 是持续过程，本质就是 [[方法/交互式学习法]]——发激励、看响应、分析盲区、调整策略。每一轮交互都在校准你对它的认知。

## 设计是 R3 问题——用 Agent 做镜子

软件设计是 R3 问题——维度不可穷举、非线性交互、没有标准答案。一个人设计容易卡在局部最优解里，自己还意识不到。

### 把 Agent 当镜子

不是让 Agent 替你决策，而是说出你的想法，看它反馈，从中发现自己没想到的东西：

- 让 Agent 从不同角色视角看设计（用户、运维、攻击者）
- 让 Agent 扮演质疑者："这个方案在什么情况下会崩？"
- 让 Agent 补充遗漏的质量维度（安全、性能、可维护性）
- 让 Agent 提替代方案——对比本身暴露盲区
- 让 Agent 审阅设计——补充边界条件、检查一致性

和同事做设计评审一个道理，但 Agent 随时在线、不会累——只是不会主动说它不知道的事。

### 防御性思考——思维陷阱怀疑的外化

R3 问题的本质决定了：沿一条设计路径走，每步看起来都合理，但可能已经走偏了。**不依赖"第一次就做对"，而是假设"第一次大概率有问题"，通过外部反馈修正。**

防御策略：

- **Agent 审阅** — 从 Agent 视角提问，发现盲区
- **用户审阅** — 每步生成过一眼，看有没有方向错误
- **多视角推演** — 从用户、运维、攻击者分别审视同一个设计
- **小步验证** — 做一部分就停下来检查，让矛盾尽早暴露

这些策略就是把 [[方法/思维陷阱怀疑]] 外化到协作流程中。

### Agent 意见的局限

Agent 的建议可能听起来合理但不可行（没见你的环境）、遗漏关键约束（不知道你的上下文）、过于自信（不会说"我不确定"）。

> **让 Agent 提供意见来帮你发现盲区，但不让它做最终决策。**
> 
> 所有涉及真实代价的判断——选哪个方案、要不要改接口、能不能上线——最终决策者必须是你。

## 设计示例：把控全局与关键

设计分成两层：**系统设计**建立掌控感并指导任务设计，**任务设计**进一步掌控不信任区并直接指导编码。

### 系统设计：建立掌控感

掌控感来自两个层面：**对系统的掌控**（结构清晰可见、可查、可改），**对协作者的初步掌控**（大概 Agent 在靠不住的地方约束或标注）。

#### 不信任区（初步）

大概地约束或标注 Agent 的**不信任区**——哪些边界、状态转换、模块 Agent 容易出错。

### 任务设计：进一步掌控不信任区

任务设计结合了前几步的成果——**系统设计的结构** + **第一步了解的沟通方法和能力边界** + **你对任务本身的知识**——把系统拆成**可直接交给 Agent 编码的子任务**，在每个子任务上把不信任区具体到信任为止：

- 每个子任务边界清晰、产出明确（一个模块、一个接口、一条流程）
- 根据 Agent 的能力边界，标注每个子任务的具体不信任区——该部分需要重点检查、约束写死、或你来兜底
- 根据对 Agent 沟通方法的了解，决定每个子任务的 prompt 怎么写最有效
- 标注子任务之间的依赖顺序——哪些必须做完才能做下一个
- 任务完成的标准（测试通过？验收清单？）

任务设计是编码的直接依据：**"实现子任务 X，特别注意边界条件 Y 和状态转换 Z，这部分不信任区必须检查。"**

任务设计也要让 Agent 审阅——它知道自己擅长什么不擅长什么，问它"这个子任务拆得合理吗？哪里你觉得难做？"可能比你自己硬分更实际。

### 审阅设计

让 Agent 看一遍设计并提问——是否遗漏边界条件、什么情况下会失败、接口是否有冲突。审阅目的不是让它批准，是**让它帮你发现盲区**。
